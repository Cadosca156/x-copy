# Пункт 5. Обмежені черги, пули та час очікування

## Проблема

Коли запити надходять швидше, ніж сервер завершує роботу, додаткова черга не створює нової потужності. Вона тримає запити, потоки, пам'ять і з'єднання. Якщо база або SMTP зависли, очікування може зайняти всі робочі потоки. Попередній executor відновлення пароля вже мав два потоки й чергу 100, але інші бюджети явно не задавалися.

Цей пункт додає захист у кількох місцях: Tomcat → допуск запиту → пул/драйвер → база чи SMTP. Значення підібрані як початкові обмеження для наявного одного backend на невеликому сервері; це не виміряна оптимальна конфігурація і не обіцянка RPS.

## Що змінилося

| Файл у `backend` | Роль |
| --- | --- |
| `src/main/resources/application.properties` | Межі Tomcat, Hikari/PostgreSQL, Redis і SMTP |
| `config/CapacityFilter.java` | Допуск без черги перед Spring Security, зверненнями до баз і multipart-парсингом |
| `config/DatabaseCapacityConfig.java` | MongoDB pool/operation timeout і обмежена черга Lettuce |
| `security/SecurityMailConfig.java` | Два працівники, 16 очікувань, явне відхилення зайвого |
| `exception/GlobalExceptionHandler.java` | Тимчасові помилки залежностей стають загальним 503 з `Retry-After` |
| `config/MongoQueryIndexMigration.java` | Окремий довший timeout адміністративних операцій міграції |

Для Java-файлів префікс — `src/main/java/com/net/cardo/xcopybackend/`.

## 1. Допуск запиту без внутрішньої черги

`CapacityFilter` — звичайний servlet filter з порядком раніше за Spring Security. Це важливо: відхилений запит не має спочатку займати SQL-з'єднання для перевірки JWT або змушувати застосунок розбирати multipart-файл.

Початкові межі:

| Ресурс | Одночасні запити на процес |
| --- | --- |
| Загальний бюджет захищених маршрутів | 32 |
| POST та інші змінювальні запити `/api/auth/`, OAuth start/callback | 4 |
| GET дописів/коментарів та стрічки підписок | 12 |
| Multipart uploads | 4 |
| Публічне читання `/media/` | 8 |

Кожен запит займає загальний дозвіл і, якщо відповідає категорії, ще один дозвіл цієї категорії. Категорії не підсумовуються поверх 32: загальна межа залишається спільною. Числа змінюються через `app.capacity.requests/auth/reads/uploads/media`; некоректні або більші за загальний бюджет значення зупиняють запуск.

Алгоритм:

1. Для `/api/`, `/media/`, `/oauth2/` та `/login/oauth2/` пробуємо `Semaphore.tryAcquire()` загального бюджету.
2. Якщо немає місця, відразу відповідаємо 503, `Retry-After: 2`, `Cache-Control: no-store` і загальним повідомленням.
3. Якщо запит важкої категорії, так само пробуємо її семафор. При відмові загальний дозвіл повертається.
4. Тільки після успішного допуску виконуємо наступні фільтри, автентифікацію і контролер.
5. У `finally` повертаємо всі отримані дозволи — навіть коли нижче виникла помилка.

`tryAcquire()` не чекає. У фільтрі немає додаткового списку очікування чи нового потоку на запит. OPTIONS пропускається, щоб цей механізм не блокував CORS preflight. Звичайна статична сторінка поза цими маршрутами захищається межами Tomcat.

503 тут означає тимчасову нестачу серверної потужності. Існуючий 429 означає інший тип обмеження: частоту дій/IP або окрему межу staging медіасервісу. Не слід автоматично повторювати POST: він міг мати побічні ефекти на іншому рівні.

Це бюджети одного JVM. Дві репліки матимуть два набори дозволів. Наявні контролери працюють синхронно; для майбутнього servlet async/streaming потрібно окремо прив'язати час утримання дозволу до завершення асинхронної роботи.

## 2. Tomcat також має скінченні межі

| Параметр | Значення | Що обмежує |
| --- | --- | --- |
| `threads.max` / `min-spare` | 48 / 8 | Робочі потоки |
| `threads.max-queue-capacity` | 64 | Черга робіт виконавця |
| `max-connections` | 128 | Прийняті з'єднання |
| `accept-count` | 32 | Запитуваний backlog приймання на рівні ОС |
| `connection-timeout` | 5 s | Очікування початкових даних з'єднання, не час усієї бізнес-операції |
| `keep-alive-timeout` | 10 s | Очікування наступного запиту на з'єднанні |

Префікс параметрів — `server.tomcat.`. Наявність `threads.max-queue-capacity` перевірена в metadata **встановленого Spring Boot 4.0.6**, а не лише в новішій вебдокументації. Віртуальні потоки не вмикалися.

Фільтр може дати зрозумілий 503 лише запиту, який уже отримав робочий потік. При перевантаженні самого Tomcat/мережі можливе закриття з'єднання або відмова приймання. Не можна обіцяти JSON-відповідь кожному клієнту під довільним flood.

## 3. PostgreSQL і Hikari

Hikari тримає максимум **8** SQL-з'єднань, мінімум **2** неактивних; отримання зайнятого з'єднання чекає максимум **2000 ms**, перевірка з'єднання — **1000 ms**.

Драйвер має `connectTimeout=3` і `socketTimeout=10` секунд. Окремо startup-параметр pgJDBC `options` задає серверні `statement_timeout=5000` та `lock_timeout=1000` мілісекунд для сесій цього застосунку. Це не глобальна зміна налаштувань PostgreSQL і не зміна схеми.

Різниця важлива:

- connection timeout — скільки чекаємо мережевого з'єднання;
- pool timeout — скільки чекаємо вільного вже керованого з'єднання;
- statement timeout — PostgreSQL скасовує надто довгий SQL;
- lock timeout — припиняє надто довге очікування SQL-блокування;
- socket timeout — обмежує бездіяльне очікування мережевої відповіді драйвером.

SQL-логування кожної команди вимкнено через `spring.jpa.show-sql=false`, щоб запити не множили обсяг логів під навантаженням. Hibernate Statistics для окремих тестів залишається доступною.

Офіційні параметри драйвера: [pgJDBC connection properties](https://jdbc.postgresql.org/documentation/use/).

## 4. MongoDB

`DatabaseCapacityConfig` налаштовує драйвер, який створює Spring Boot:

- максимум 16 з'єднань на сервер MongoDB, мінімум 0;
- максимум два одночасні встановлення нових з'єднань;
- вибір доступного сервера та connect timeout — по 2 секунди;
- client-side operation timeout (CSOT) — 5000 ms, включно з очікуванням з'єднання для операції.

CSOT обмежує конкретну операцію драйвера, не весь HTTP-запит із кількох SQL/MongoDB/Redis-команд. Значення pool/CSOT можна змінити через `app.mongodb.max-pool-size` та `app.mongodb.operation-timeout-ms`.

Міграція індексів — адміністративна робота до приймання HTTP-запитів. Її `MongoDatabase` використовує окремий timeout **120 секунд**, щоб звичайний п'ятисекундний бюджет читання не обривав побудову індексу. Це бюджет адміністративних операцій/курсорів, а не гарантія завершення всієї міграції за дві хвилини. Попередній протокол повторного запуску й архівації збережений.

Опис пулів та CSOT: [MongoDB Java driver connection pools](https://www.mongodb.com/docs/drivers/java/sync/current/connection/specify-connection-options/connection-pools/).

## 5. Redis

Lettuce в цьому проєкті використовує спільне мультиплексоване з'єднання. Додавати лише властивості Apache connection pool без відповідного пулу не означало б обмежити реальну чергу команд.

Тому connect timeout — 1 секунда, command/read timeout — 2 секунди, а `ClientOptions.requestQueueSize` обмежено 64 командами на з'єднання. При відключенні встановлено `REJECT_COMMANDS`: нові команди не накопичуються в нескінченній offline-черзі. Автоматичне перепідключення залишається.

Customizer змінює builder опцій Boot, зберігаючи його налаштування сокета/SSL. Це не глобальний ліміт усіх команд усіх можливих з'єднань. Поточний deployment використовує окремий Redis, без Cluster.

## 6. Пошта й асинхронна черга

SMTP connection timeout — 3000 ms, читання і запис — по 5000 ms. Це окремі таймаути етапів, а не одна обіцянка «лист завжди завершиться за 5 секунд».

`securityMailExecutor` має два потоки і 16 очікувань. Два заблоковані SMTP-завдання плюс 16 у черзі означають, що наступне відхиляється через `AbortPolicy`. `CallerRunsPolicy` не використовується: інакше HTTP-потік сам почав би відправляти лист у момент перевантаження.

`TaskRejectedException` обробляється як загальний 503. Для відновлення пароля це спільний стан черги, незалежний від того, чи існує конкретний email. За нормального допуску зберігається порожня відповідь 202 для відомої та невідомої адреси. 202 не гарантує подальшої доставки листа: асинхронна помилка, як і раніше, логуються без адреси/секрету.

## 7. Помилки та повторення

`GlobalExceptionHandler` перетворює тимчасові помилки доступу до баз, SQL-таймаути, відмову черги та `MailException` на загальний 503 із `Retry-After: 2`. Відповідь не розкриває SQL, hostname, SMTP-пароль чи текст внутрішнього винятку.

Несподівані помилки програмної логіки не перетворюються всі підряд на 503: інакше реальні баги маскувалися б під навантаження. Відмова SMTP може бути наслідком конфігурації, а не лише перевантаження, тому потрібен перегляд серверних логів.

Автоматичних повторів записів не додано. Timeout не доводить, що запис не відбувся. Для безпечного автоматичного повторення створення дописів у майбутньому потрібні idempotency keys.

## Як перевіряється

`CapacityFilterTest` утримує один запит, перевіряє відмову іншого тієї ж категорії та доступність читання, повернення дозволів після IOException, загальний ліміт і відхилення upload до читання тіла.

`MailQueueCapacityTest` фактично займає два працівники, заповнює 16 місць і перевіряє відхилення наступного. `CapacityErrorResponseTest` перевіряє 503/Retry-After та відсутність приватного тексту помилки. `DatabaseCapacityConfigTest` перевіряє зібрані опції драйверів.

`CapacityIntegrationTests` запускає реальний Tomcat: два запити тримають його тестовий endpoint, третій отримує 503, після звільнення робота відновлюється. Другий сценарій перевіряє справжні PostgreSQL session settings і скасування `SELECT pg_sleep(6)` серверним лімітом у 5 секунд. Ці тести використовують тільки окремі CI-бази.

Локальний `./gradlew unitTest` не потребує баз. Повний `check` запускається з ізольованими PostgreSQL/MongoDB/Redis у CI. Опис властивостей контейнера: [Spring Boot application properties](https://docs.spring.io/spring-boot/appendix/application-properties/index.html).

## Як розповісти на співбесіді

«Я не збільшував черги в надії, що сервер витримає більше. Я задав бюджети на різних рівнях: скінченні потоки й чергу Tomcat, семафори допуску перед автентифікацією та multipart, обмежені з'єднання до баз і час очікування, малу чергу відправлення листів. Перевантажений запит відхиляється рано, дозволи повертаються через finally. Різні категорії мають свої межі, тому зайнятий вхід не забирає всі місця читання стрічки. Я перевірив відмову й відновлення, а SQL-таймаут — реальною повільною командою на тестовій базі. Це контрольоване погіршення під навантаженням, а не доказ конкретної пропускної здатності».
