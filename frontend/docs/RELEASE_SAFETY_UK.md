# Підготовка до релізу: перші три виправлення

## Стан змін

Фронтенд змінений у поточному проєкті. Бекенд підготовлений в ізольованій копії
`frontend/.release-hardening/backend`, оскільки поточна робоча папка дозволяє запис
тільки в `frontend`. Оригінальний `backend` та production не змінені.

Для оригінального бекенду підготовлений `frontend/docs/backend-release-safety.patch`.
Патч містить лише зміни бекенду: повторно застосовувати фронтенд не потрібно.
Ізольована гілка: `fix/release-account-safety`.

## 1. Одночасні зміни профілю й пароля

`User.rowVersion` — поле JPA `@Version`. Збереження профілю або аватара, прочитаного
до скидання пароля, завершується HTTP 409. Старі пароль і версія облікових даних
не повинні записуватися поверх нових. Bulk-запит встановлення першого пароля
також збільшує `rowVersion`.

Додані інтеграційні тести для обох випадків у `RedisSessionIntegrationTests`.
Їх потрібно виконати з PostgreSQL і Redis перед застосуванням у production.

Схема потребує нового поля `users.row_version bigint not null default 0`.
У поточній конфігурації його додає Hibernate `ddl-auto=update`. Перехід на
контрольовані міграції залишається окремим наступним етапом; не вимикати
автоматичне оновлення схеми до підготовки міграції.

## 2. Незавершена реєстрація

До підтвердження коду SQL-акаунта немає. Тимчасовий запис Redis містить адресу,
BCrypt-хеш пароля та BCrypt-хеш коду, живе п'ять хвилин. Відкритий пароль не
зберігається. Повторне надсилання зберігає строк дії та бюджет спроб.

Акаунт створюється після правильного коду та атомарного використання challenge.
Якщо за цей час адреса вже отримала акаунт, зокрема через Google, реєстрація
відхиляється: тимчасовий пароль не приєднується до цього акаунта.
У відповіді нового входу `userId` тепер `null`; фронтенд використовує `challengeId`.

Це захищає нові реєстрації. Старі записи, створені до підтвердження пошти,
неможливо надійно відрізнити за поточною схемою. Перед масовим запуском потрібне
окреме рішення щодо таких акаунтів; автоматичного видалення чи скидання їхніх
паролів ці зміни не виконують.

## 3. Повторне створення постів

Фронтенд зберігає `Idempotency-Key` для незміненої чернетки після невизначеної
помилки. Успіх або редагування тексту/вибраного файла створює нову операцію.
Подвійне натискання використовує один запит. Ключ живе у відкритому компоненті;
перезавантаження сторінки або закриття компонента його не зберігає.

Бекенд утворює MongoDB `_id` із користувача та ключа, використовує `insert`,
а не перезапис. Унікальність `_id` захищає одночасні запити з кількох процесів.
Змінений вміст із тим самим ключем повертає 409. Відбиток охоплює текст,
тип і байти файла. Після видалення залишається мінімальний tombstone без тексту
та медіа; повтор старої операції повертає 410 і не відновлює пост.

Помилка Redis під час інвалідації кешу не змінює результат вже завершеного запису.
У цьому випадку сторінки кешу можуть залишатися старими до їхнього TTL — 30 секунд.
Старий клієнт без заголовка продовжує працювати через попередній контракт,
без гарантії ідемпотентності. Для production потрібне узгоджене оновлення клієнта.

Невизначений результат MongoDB-вставки з файлом не спричиняє негайного видалення
файла: база могла вже зберегти посилання. Це безпечніше для даних, але може залишити
невикористаний файл. Надійне прибирання таких файлів потребує окремого механізму.

## Перевірки

- Фронтенд: 22 тести, ESLint і production build успішні.
- Увесь Java-код і тести скомпільовано локальним JDK 21 з `--release 17`.
- Окремий JUnit-запуск: 200 тестів успішні; 4 тести `BrowserSecurityFlowTest`
  заблоковані забороною локальних мережевих з'єднань у середовищі.
- Стандартний Gradle-запуск заблокований тим самим обмеженням локального з'єднання
  з daemon. Docker engine недоступний, тому інтеграційні сценарії з реальними БД,
  включно з новими тестами гонок, і браузерний E2E тут не виконані.

Перед релізом виконати звичайний CI `check bootJar`, фронтенд-перевірки та E2E.
Наявність патча не означає готовності до production.

## Застосування

Відкрити корінь `D:\progs\x-copy` як робочу папку. У корені проєкту:

```powershell
git switch -c fix/release-account-safety
git apply --check frontend/docs/backend-release-safety.patch
git apply frontend/docs/backend-release-safety.patch
```

Якщо перевірка патча не проходить, зупинитися й узгодити зміни з новим станом
бекенду. Не застосовувати патч примусово. Після застосування запускати перевірки
та комітити разом з уже підготовленими змінами фронтенду.

## Наступні етапи

1. Резервні копії PostgreSQL, MongoDB і медіа, перевірка узгодженого відновлення
   на ізольованому середовищі. Потрібні доступ до сервера й місце для копій.
2. Метрики затримки, помилок і ресурсів, сповіщення, перевірки готовності залежностей,
   контрольований rollback.
3. Навантажувальний тест на копії даних: стрічка, підписки, популярний пост,
   створення постів, вхід і медіа. Визначити допустимі затримки й частку помилок.
4. За результатами вимірювань — об'єктне сховище/CDN, черга пошти, масштабування,
   оптимізація підписок і лічильників.

Налаштування firewall, доступи адміністраторів, залежності, політика email,
модерація та захист від масового створення акаунтів потребують окремої перевірки.
