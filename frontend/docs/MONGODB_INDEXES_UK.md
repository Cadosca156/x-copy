# Як я додав індекси MongoDB і захистив лайки від дублікатів

Це другий крок оптимізації після пакетного завантаження стрічки. Перший крок скоротив кількість звернень до баз. Другий допомагає самій MongoDB швидше знаходити та впорядковувати потрібні документи.

## 1. Проблема і мета

Стандартний індекс _id прискорює пошук за ID документа. Але наші запити зазвичай мають інші умови: автор, ID допису, користувач та сортування за датою.

Без відповідного індексу база може перебирати багато документів — COLLSCAN. Якщо порядок потрібної видачі не підтримується індексом, може додаватися окремий етап SORT.

Індекс — додаткова впорядкована структура, яка допомагає знаходити документи за значеннями полів. Він займає місце та має оновлюватися під час записів. Тому я додав індекси під конкретні запити, а не під кожне поле.

## 2. Чотири індекси та їх призначення

| Колекція | Назва нового індексу | Поля у точному порядку | Запит, якому він відповідає |
|---|---|---|---|
| posts | posts_created_id_v1 | createdAt: -1, _id: -1 | Загальна стрічка від нових до старих |
| posts | posts_user_created_id_v1 | userId: 1, createdAt: -1, _id: -1 | Дописи одного автора з тим самим сортуванням |
| comments | comments_post_created_id_v1 | postId: 1, createdAt: -1, _id: -1 | Коментарі допису з сортуванням; також фільтр/лічильник за postId |
| likes | likes_post_user_unique_v1 | postId: 1, userId: 1, unique | Пошук власного лайка, лічильники за postId, заборона повторної пари |

Напрямок 1 означає зростання, -1 — спадання. В індексах дописів та коментарів _id додає однозначний порядок, коли createdAt збігається. Java-поле id відображається в MongoDB як _id.

Окремий індекс лише на likes.postId не додається: postId уже є першим полем складеного індексу лайків. Такий префікс може використовуватися для відповідного фільтра. Аналогічно індекс коментарів починається з postId.

### Чому порядок полів важливий

Для профілю спочатку є точна умова userId = конкретний автор, а потім сортування за createdAt та _id. Тому поле рівності userId стоїть першим.

Це відповідає принципу Equality–Sort–Range: точні умови спочатку, далі поля сортування. [Офіційне пояснення MongoDB ESR](https://www.mongodb.com/docs/v8.0/tutorial/equality-sort-range-guideline/).

Індекс (userId, createdAt, _id) не замінює індекс (createdAt, _id) для загальної стрічки: коли автор не заданий, перший індекс упорядкований насамперед за авторами. [Правила використання індексів для сортування](https://www.mongodb.com/docs/v8.0/tutorial/sort-results-with-indexes/).

Складений індекс є впорядкованою послідовністю полів. Перевірка в коді порівнює порядок ключів, а не лише їхні назви та значення.

## 3. Як це доставляється через код

Новий клас бекенду — MongoQueryIndexMigration у пакеті config.

Він реалізує InitializingBean. Spring виконує міграцію під час ініціалізації singleton-компонентів, до завершення запуску застосунку та приймання запитів. Це важливо: база має отримати обмеження унікальності до роботи нового коду з лайками.

Міграція:

1. Створює потрібні колекції, якщо їх ще немає.
2. Читає метадані наявних індексів.
3. Створює відсутні індекси.
4. Для лайків проводить контрольоване перетворення індексу на унікальний.

Список метаданих індексів слугує перевіркою стану. Окрема таблиця версій міграцій для цих чотирьох визначень не потрібна: повторний запуск перевіряє фактичні ключі та unique.

Поведінка при вже наявних індексах:

- Еквівалентний повний індекс використовується повторно, навіть якщо його створили вручну під іншою назвою.
- Якщо наша назва вже зайнята іншими ключами, запуск зупиняється з поясненням.
- Часткові, sparse, приховані індекси та індекси з collation автоматично не вважаються еквівалентними.
- Код не видаляє старі індекси та не перебудовує їх мовчки.

Таким чином, успішний повторний запуск не створює ще одну копію того самого індексу. Конфліктна конфігурація потребує окремої перевірки замість автоматичного dropIndex.

## 4. Навіщо унікальний індекс лайків

Логічне правило: один користувач може мати лише один активний лайк одного допису.

Перевірки в Java недостатньо. Два паралельні запити можуть виконатися так:

```text
Запит A: лайка ще немає
Запит B: лайка ще немає
Запит A: вставляє документ
Запит B: теж вставляє документ
```

Унікальний індекс на (postId, userId) переносить це правило до бази. Обидва запити не зможуть створити однакову пару.

Важливо, що унікальною є саме пара. Інша людина може лайкнути цей самий допис; цей самий користувач може лайкнути інший допис.

## 5. Чому не можна одразу створити unique

Якщо у старій колекції вже є повторні пари, перетворення на unique завершиться помилкою. Просте видалення всіх повторів без копії також було б поганим способом міграції даних.

Я використав механізм MongoDB prepareUnique з подальшим архівуванням. Він підтримується починаючи з MongoDB 6; у проєкті використовується MongoDB 8.

Послідовність:

1. Створити або знайти звичайний складений індекс лайків.
2. Перевірити, що postId і userId у старих документах є непорожніми рядками. Некоректні значення зупиняють міграцію до очищення даних.
3. Увімкнути prepareUnique окремою командою collMod.
4. Пройти старі документи в порядку складеного індексу та обробити повторні пари.
5. Провести dryRun перевірку перетворення.
6. Увімкнути unique.
7. Очистити кеш стрічок, щоб попередні лічильники з дублікатами не залишилися в кеші.

prepareUnique забороняє нові дублікати, поки старі ще можуть залишатися у колекції. Це закриває проміжок між очищенням і ввімкненням остаточного unique. [Офіційний порядок перетворення індексу](https://www.mongodb.com/docs/manual/core/index-unique/convert-to-unique/).

Приклад команд за змістом:

```javascript
db.runCommand({
  collMod: "likes",
  index: { name: "likes_post_user_unique_v1", prepareUnique: true }
});

// Тут код архівує повтори та залишає одну активну копію пари.

db.runCommand({
  collMod: "likes",
  index: { name: "likes_post_user_unique_v1", unique: true },
  dryRun: true
});

db.runCommand({
  collMod: "likes",
  index: { name: "likes_post_user_unique_v1", unique: true }
});
```

Це пояснювальний приклад. Штатний запуск виконує ці дії через міграцію; вручну дублювати їх для звичайного деплою не потрібно.

## 6. Як зберігаються повторні документи

Для кожної однакової пари перший зустрінутий документ залишається активним. Політика не обіцяє вибирати найстарішу дату createdAt; логічний стан «користувач лайкнув допис» однаковий для кожної копії.

Решта зберігаються в окремій колекції likes_duplicate_archive_v1. Архівний запис містить:

- первинний _id;
- назву джерела та причину архівування;
- час архівування;
- повну копію початкового документа, включно з додатковими старими полями.

Тільки після підтвердження запису копії код видаляє відповідний документ з активної likes.

Для архіву використовується JOURNALED write concern: підтвердження має враховувати журнал MongoDB. Якщо архівування завершується помилкою, до видалення цього документа код не доходить.

Архів записується через upsert із $setOnInsert та тим самим _id. Якщо запуск перервався після архівування, повторна спроба не створює другу архівну копію та не перезаписує попередню.

Перед видаленням код також читає архівний запис і порівнює збережений документ з активним. Якщо під тим самим ID уже лежить інший або пошкоджений знімок, міграція зупиняється замість видалення оригіналу.

Документи читаються курсором із batchSize 256. Однакові пари йдуть поруч завдяки індексу. У Java зберігається попередня пара, а не весь набір лайків. Не використовується великий $push-масив усіх дублікатів.

Підсумок для трьох однакових лайків:

```text
Було: likes = A, B, C для однієї пари
Стало: одна активна копія; дві повні копії в архіві
```

Лічильник активних лайків зменшиться до одного — це виправлення даних, а не просто прискорення запиту. Архів не має автоматичного TTL: його зберігання та подальше видалення — окрема адміністративна дія.

## 7. Обробка одночасних запитів у LikeService

Додав обробку DuplicateKeyException навколо вставки лайка.

Якщо інший запит уже вставив ту саму пару, сервіс перевіряє її наявність і повертає true — стан «лайк є». Кеш інвалідується, як і після звичайного успішного лайка.

Якщо відповідної пари насправді немає, виняток не приховується: це може бути інший конфлікт унікальності або інша проблема.

Це обробляє змагання двох додавань. Воно не робить довільну послідовність одночасних «додати/зняти/додати» єдиною атомарною операцією. Остаточний захист від двох активних копій забезпечує MongoDB.

## 8. Як перевіряється, що індекс справді працює

Перевірити getIndexes недостатньо: індекс може існувати, але планувальник не вибирати його для потрібного запиту.

Інтеграційний тест додає по 500 тестових документів і виконує explain з executionStats для:

- загальної стрічки;
- сторінки одного автора;
- коментарів одного допису;
- пошуку конкретного лайка.

Тест перевіряє winningPlan, а не весь список кандидатів. Він вимагає потрібний indexName, відсутність COLLSCAN та блокувального SORT, а також не більше 20 переглянутих документів для цих запитів із limit 20.

hint у цих перевірках планів не задається: рішення має прийняти сама база. hint використовується лише всередині міграції для впорядкованого читання повторів.

Це доказ на контрольованих даних і конкретних формах запиту. Результат не встановлює межу одночасних користувачів або гарантований час відповіді.

### Випадки, які не слід узагальнювати

- Стрічка підписок використовує $in за кількома авторами. План залежить від розміру списку та розподілу даних; відсутність SORT не гарантується для будь-якого великого списку.
- Глибока offset-пагінація все ще може переглядати багато ключів, навіть з індексом.
- Підрахунок великої кількості лайків усе одно потребує роботи з відповідними записами або ключами.
- Нові індекси збільшують витрати на вставки, видалення, диск і пам’ять.

## 9. Які тести додано

MongoIndexKeyOrderTest перевіряє, що порядок полів і напрямки не плутаються при порівнянні визначень.

LikeServiceConcurrencyTest перевіряє змагання двох вставок, звичайне зняття лайка та передачу стороннього DuplicateKeyException нагору.

MongoQueryIndexMigrationIntegrationTests перевіряє:

1. Створення чотирьох індексів та повторний запуск.
2. Архівування зайвих копій із повним збереженням документа.
3. Заборону нових дублікатів і дозвіл інших пар.
4. Продовження після prepareUnique та повторне використання індексу під іншою назвою.
5. Відсутність видалень, якщо архів не приймає запис; успішне продовження після усунення причини.
6. Зупинку на некоректних старих ID.
7. Відмову мовчки замінювати конфліктний індекс.
8. Фактичні плани основних запитів.

У тестах кожна міграція працює у власній випадково названій базі з префіксом xcopy_index_test_. Видаляється тільки створена тестом база. Робоча база для цих перевірок не використовується.

Попередній PostFeedBatchIntegrationTests також оновлено: після ввімкнення унікальності повторна вставка повинна відхилятися базою, а не створювати ще один Like-документ.

## 11. Що відбудеться після деплою

На першому запуску нового бекенду міграція створить індекси та, якщо потрібно, обробить старі повторні лайки. На наступних запусках уже готовий unique-індекс не очищається заново.

Побудова індексів та перший прохід великих колекцій потребують CPU, I/O й часу. Початковий запуск може бути довшим. У поточній архітектурі один бекенд; одночасний запуск міграції кількома репліками не є окремо організованим сценарієм розгортання.

Сервер MongoDB має підтримувати prepareUnique/конвертацію, а користувач бази — мати права створювати індекси та виконувати collMod. При помилці міграції запуск зупиняється; винятки не приховуються. Помилкові індекси або нестандартні старі дані потребують перевірки перед повторним деплоєм.

Уся процедура не є однією транзакцією. Після переривання частина повторів може вже бути архівована та прибрана, а індекс — залишитися в prepareUnique. Повторний запуск перевіряє поточний стан і продовжує конвертацію; він не відновлює старі дублікати.

Перед першою міграцією реальних даних доцільна резервна копія. Архівування зайвих лайків захищає саме ці документи та не замінює резервну копію всієї бази.

Повернення попереднього коду не видаляє індекси й не повертає дублікати автоматично. Відновлення архівних копій конфліктуватиме з unique, тому відкат даних має бути окремою продуманою операцією.

Ця гілка продовжує пункт 1: спочатку потрібна оптимізація пакетних запитів із PR #20. У PR пункту 2 базою є гілка пункту 1, щоб показувати тільки нові зміни.

## 12. Як розповісти на співбесіді

«Після усунення N+1 я перевірив форми запитів і додав складені індекси під їхні фільтри та сортування. Для профілю першим іде userId, далі createdAt та _id; для загальної стрічки потрібен окремий індекс без префікса автора. Для лайків я зробив пару postId–userId унікальною, тому два паралельні запити вже не можуть створити два активні лайки. Старі дублікати обробляє повторювана міграція: спочатку prepareUnique блокує нові повтори, потім зайві документи архівуються й видаляються з активної колекції, після dryRun вмикається unique. Я перевірив збої архівування, повторний запуск і плани explain на реальній MongoDB. Це оптимізація доступу до даних, а фактичний приріст пропускної здатності потрібно вимірювати навантажувальним тестом».

### Запитання, до яких варто бути готовим

**Чому не достатньо @Indexed?** Окрім декларації індексу, тут потрібне кероване перетворення старих даних і захист від повторів у процесі конвертації. Міграція явно задає ці кроки.

**Чому не просто exists перед insert?** Два запити можуть одночасно побачити відсутність лайка. Остаточне обмеження має забезпечувати база.

**Чи губляться зайві Like-документи?** В активній колекції залишається одна копія пари, а кожна вилучена копія попередньо зберігається повністю в архіві.

**Як довести, що індекс корисний?** Перевірити winningPlan і executionStats для реальних форм запитів: який індекс обрано, чи є COLLSCAN/SORT, скільки ключів і документів переглянуто.

**Чи всі запити стали швидкими?** Ні. Покриті конкретні основні форми; великі $in, offset-пагінація та дуже великі лічильники потребують окремих замірів і наступних оптимізацій.
