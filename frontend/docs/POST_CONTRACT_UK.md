# Контракт дописів

## Що змінилося і чому

Фронтенд більше не вгадує поля `postId`, `text`, `likeCount`, вкладеного `author` тощо. Він читає фактичний плоский `PostResponse`. Це запобігає прихованим помилкам на кшталт перетворення рядка `"false"` на логічне `true` або створення вигаданого ID.

`src/api/postContract.js` перевіряє JSON під час створення допису й завантаження кожного елемента стрічки, профілю та підписок. Некоректна відповідь дає зрозумілу помилку замість частково неправильного відображення. Нові додаткові поля дозволені, перейменування наявних потребує узгодженої зміни контракту.

## Формат відповіді

| Поле | Тип |
| --- | --- |
| `id` | непорожній рядок |
| `userId`, `username`, `displayName` | рядок або `null` |
| `content`, `mediaType`, `mediaUrl`, `avatarUrl` | рядок або `null` |
| `createdAt` | локальний ISO datetime з секундами, необов'язковою дробовою частиною, або `null` |
| `likesCount`, `commentsCount` | невід'ємне ціле число |
| `likedByMe` | boolean |

Усі перелічені ключі обов'язкові. Nullable-поля збережено для старих записів і видалених авторів. Час залишається наявним `LocalDateTime` без часового поясу; ця зміна не мігрує часові дані.

## Створення допису

`POST /api/posts` приймає multipart-поля `content` і необов'язкове `file`. Ліміт нового тексту — **280 одиниць UTF-16**, як у JavaScript `length`, HTML `maxLength` та Java `String.length()`. Наприклад, 140 emoji `😀` займають 280 одиниць. Це не підрахунок видимих графем.

Спочатку перевіряється довжина початкового тексту, потім прибираються крайові пробільні символи за правилами JavaScript `trim()`, включно з NBSP та BOM. Потрібен непорожній текст або непорожній файл. Порожній допис чи перевищення ліміту повертає **400**. Окремі перевірки безпеки файлів зберігаються.

У бекенді правила зосереджені в `PostRules` і застосовуються на початку `PostService.createPost()`, до запису файлу або документа. Контролер передає початковий текст, щоб попереднє обрізання пробілів не обходило ліміт. На фронті той самий ліміт використовують форма й API-клієнт. Серверна перевірка обов'язкова, бо клієнт можна обійти.

Старі довгі дописи залишаються доступними для читання. Дані в базі не переписуються. Правила коментарів у цій зміні не змінюються.

## Як перевіряється сумісність

Спільний приклад `contracts/post-response.json` читають Java-тест серіалізації HTTP-відповідей створення/стрічки та JavaScript-тест парсера. Тому зміна типу або назви поля перестане проходити тести однієї зі сторін. Окремі тести перевіряють межу 280, emoji, пробіли, порожні файли, старі довгі дописи та відхилення помилкових типів. Наскрізний тест надсилає некоректні multipart-запити безпосередньо реальному серверу, обходячи форму.
