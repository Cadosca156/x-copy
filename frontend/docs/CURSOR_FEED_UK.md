# Пункт 6. Пагінація стрічки за останнім дописом

## Що було і що стало

Номер сторінки перетворюється на offset: сторінка 1000 по 20 дописів означає пропустити 20000 результатів. Індекс допомагає сортуванню, але не робить пропуск довгого префікса безкоштовним. Новий допис на початку також зміщує номери елементів між двома читаннями.

Нова стрічка запам'ятовує **позицію останнього показаного допису**, а не кількість уже переглянутих елементів. Наступна вибірка шукає записи строго після цієї позиції у порядку сортування. Загальна стрічка, профіль і підписки використовують цей протокол.

Опис різниці offset та range pagination: [MongoDB cursor.skip() — range queries](https://www.mongodb.com/docs/manual/reference/method/cursor.skip/).

## 1. Чому курсор має два поля

Сортування залишається `createdAt DESC, _id DESC`. Пара `(createdAt, id)` задає позицію. Якщо обмежитися тільки `createdAt < останняДата`, всі ще не показані дописи з тією ж датою будуть пропущені.

Приклад: A, B, C мають однакову дату, а порядок ID — C > B > A. Показали C і B. Наступний запит має повернути A, хоча його дата дорівнює даті B.

Тому критерій для наступного вікна:

```text
createdAt < lastCreatedAt
OR
(createdAt == lastCreatedAt AND _id < lastId)
```

Порівняння строгі (`<`), тому граничний допис не повторюється. Фільтр конкретного автора або набору підписок додається сервером разом із цим критерієм; курсор не замінює перевірку доступу.

## 2. Що містить непрозорий рядок

`FeedCursor` записує у двійковий буфер:

1. Версію формату — зараз 1.
2. Область: `all`, `author:<UUID>` або `following:<viewerUUID>`.
3. Дату останнього елемента з точністю до мілісекунд.
4. Його ID.

Потім кодує буфер у Base64 URL-safe без padding. Це дозволяє передавати позицію одним query-параметром. Двійковий формат не потребує додаткового JSON-парсера.

MongoDB зберігає Date з точністю до мілісекунд; курсор будується з **прочитаного з бази** допису. LocalDateTime кодується й відновлюється як те саме календарне значення через UTC-представлення в транспорті. Цей пункт не змінює існуючу часову модель бази: timezone конвертера MongoDB має залишатися узгодженим між процесами та запусками.

Це **не секрет і не токен авторизації**, шифрування або підпис не додаються. Користувач може змінити позицію й отримати інше допустиме вікно. Він не може через неї змінити серверний фільтр автора/підписок чи розмір понад ліміт.

При читанні перевіряються довжина до 600 символів, URL-safe алфавіт, версія, очікувана область, повнота формату, ID до 128 символів, відсутність зайвих байтів та канонічне повторне кодування. Неправильний курсор дає 400 до читання сторінки/кешу/метаданих. Автентифікація запиту й визначення поточного користувача відбуваються окремо раніше.

Курсор загальної стрічки не приймається як курсор профілю або підписок. Для підписок область включає глядача, тому курсор іншого користувача також не підходить.

## 3. Запит до MongoDB

`PostWindowRepositoryImpl` використовує `MongoTemplate` і критерій вище. Він додає серверний фільтр автора, стабільне сортування, `limit` максимум 51 і `maxTime` 3 секунди. `skip` не викликається. Spring QueryMapper переводить Java-поле `id` у MongoDB `_id` та стандартний hex-ID у ObjectId.

Поточні дописи створюються з MongoDB ObjectId і непорожнім `createdAt`. Записи без дати не беруть участь у новій стрічці: для історичних некоректних даних потрібне окреме перевірене відновлення дат. На цьому етапі дані автоматично не переписуються.

Для історично змішаних BSON-типів `_id` потрібен окремий аудит: унікальний tie-breaker має мати узгоджений тип. Одного Java-типу String недостатньо, щоб довести однаковий BSON-тип вручну створених документів. Звичайні ID, згенеровані поточною моделлю, перевірені інтеграційними тестами.

Індекси з пункту 2 відповідають сортуванню: `createdAt,_id` для загальної стрічки та `userId,createdAt,_id` для автора. Для великої кількості підписок ціна `$in`, читання списку авторів і план сортування все ще залежать від даних. Цей пункт прибирає залежність від **номера сторінки**, але не всі можливі витрати MongoDB.

## 4. Навіщо отримувати `size+1`

Нехай клієнт просить 20 дописів:

1. Перевіряємо `1 <= size <= 50`.
2. Просимо максимум 21 допис.
3. Якщо отримали 21, показуємо перші 20, ставимо `hasMore=true` і формуємо курсор із **20-го**, а не 21-го.
4. Якщо отримали 20 або менше, це останнє вікно: `hasMore=false`, `nextCursor=null`.
5. Автори/лайки/коментарі підвантажуються тільки для видимих дописів. Додатковий елемент не запускає зайвого доповнення відповіді.

Окремого `countDocuments()` для кількості всіх результатів немає. Рівно 20 записів в останньому вікні не змушують користувача натискати зайву кнопку для порожньої відповіді.

## 5. HTTP-контракт і сумісність

Перше вікно:

```http
GET /api/posts?pagination=cursor&size=20
```

Продовження:

```http
GET /api/posts?pagination=cursor&size=20&cursor=<nextCursor>
```

Приклад відповіді для порожньої стрічки:

```json
{
  "items": [],
  "nextCursor": null,
  "hasMore": false
}
```

Для непорожньої стрічки `items` містить звичайні об'єкти `PostResponse`. Якщо є продовження, `hasMore=true`, а `nextCursor` — рядок. Для профілю використовується `/api/posts/user/<UUID>`, для підписок — `/api/users/me/following/posts`, з тими самими query-параметрами.

Параметр `page` одночасно з `pagination=cursor` відхиляється через 400, щоб не приховувати неоднозначний запит.

**Старий HTTP-режим з масивом і `page` залишений для сумісності**, включно з його попередніми обмеженнями. Він усе ще використовує offset і не стає дешевим завдяки цьому пункту. Нові Feed/Profile/following клієнти його не викликають. Коментарі також залишилися на старій окремій пагінації: цей пункт стосується дописів.

Для поетапного rollout спочатку потрібно розгорнути backend, який підтримує обидва режими, а потім новий frontend. Старий frontend продовжує працювати з новим backend. Новий frontend не вдає, що стара відповідь-масив містить справжній курсор: некоректний контракт дає зрозумілу помилку. Якщо автоматичне оновлення frontend випередить backend, до завершення backend-deploy може знадобитися повторне завантаження стрічки.

## 6. Фронтенд

`feedPagePath()` формує URL через `URLSearchParams`, тому курсор не розбивається на додаткові параметри. `readFeedPage()` перевіряє контракт та узгодженість `hasMore/nextCursor`.

Компоненти зберігають `nextCursor` замість `nextPage`. «Завантажити ще» передає отриманий рядок без його розбору, додає елементи за ID та замінює курсор серверним значенням. При помилці курсор не пересувається: користувач може повторити читання.

При оновленні стрічки чи зміні вкладки починається новий прохід з `cursor=null`. Наявний `feedRevision` відкидає відповідь старого load-more після перемикання вкладки. Створення допису або зміна підписок запускає оновлення першого вікна.

## 7. Кеш і конкурентні зміни

Кешується тільки спільне перше вікно загальної стрічки/автора під позицією `cursor:start`; воно використовує ті самі версії області з пункту 3. Продовження читаються без кешу, щоб довільні допустимі курсори не створювали багато Redis-ключів. Стрічка підписок залишається без кешу сторінок.

Важливі випадки:

| Зміна між читаннями | Поведінка |
| --- | --- |
| Новий допис перед уже показаними | Не зміщує продовження; з'явиться після оновлення початку |
| Видалення граничного допису | Курсор усе ще працює: дата та ID містяться в ньому, `findById(anchor)` не потрібний |
| Однакові дати | ID однозначно продовжує порядок без повтору межі |
| Видалення ще не показаного допису | Він не повертається; наступні доступні записи заповнюють вікно |
| Пізня вставка зі старою датою | Може з'явитися у наступних вікнах |
| Зміна підписок | Фільтр авторів читається актуальний; UI починає прохід наново |

Це не знімок бази на весь сеанс прокручування, не real-time синхронізація і не гарантія побачити кожен допис при довільному редагуванні дат. Поле сортування має залишатися незмінним для стабільного проходу. Уже показане видалення з іншої вкладки зникне після оновлення, як і раніше.

## Перевірки

- `FeedCursorTest`: точний round-trip, область, неправильний/надмірний/обірваний формат.
- `PostWindowServiceTest`: lookahead не видається і не доповнюється метаданими; курсор із останнього видимого; перевірки до I/O; порожні підписки; продовження без lookup граничного допису та без кешування довільних позицій.
- `PostWindowQueryTest`: нульовий skip, обмежений limit і строгий tie-breaker.
- `PostFeedBatchIntegrationTests`: реальний Spring Data fragment; 20 дописів з однаковою датою; нова вставка і видалена межа між вікнами; повний прохід без пропусків і повторів.
- `PostWindowQueryIntegrationTests`: 1000 документів у власній одноразовій MongoDB-базі; ранні й глибокі позиції, загальна стрічка й автор; `explain` перевіряє потрібний індекс, відсутність COLLSCAN/звичайного SORT і обмежену кількість прочитаних документів.
- Frontend unit: параметри URL, кодування, відсутність `page`, точне завершення за серверним lookahead та відмова на неправильному контракті.
- Браузерний E2E: прокручування загальної стрічки при вставці/видаленні межі, завершення профілю, підписки, неправильний курсор і змішування двох режимів.

Плани запитів і ці сценарії доводять властивості конкретної реалізації/набору даних. Вони не замінюють навантажувальний тест із реальним розподілом авторів і підписок.

## Як розповісти на співбесіді

«Я замінив номер сторінки на keyset pagination. Раніше глибоке читання змушувало базу пропускати довгий префікс, а вставки на початку зміщували сторінки. Тепер порядок задається датою та унікальним ID. Курсор містить позицію останнього видимого елемента, наступний запит використовує строгий діапазон за цією парою та індекс. Беру size+1 для hasMore без загального count. Курсор прив'язаний до області, але не є дозволом доступу: сервер сам додає фільтри. Я перевірив однакові дати, видалену межу та вставку між читаннями, а explain на глибоких позиціях підтвердив індексований запит без skip. Стабільність порядку не означає знімок бази на весь сеанс».
