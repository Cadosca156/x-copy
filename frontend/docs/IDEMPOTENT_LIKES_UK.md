# Лайки, які можна безпечно повторити після втрати відповіді

## Проблема toggle

Старий `POST /api/posts/<id>/like` означає «перемкнути поточний стан». Якщо сервер уже поставив лайк, але відповідь загубилася, повторення того самого запиту прибере його. Унікальний індекс тут не допомагає: дубліката немає, але повторення змінило намір користувача на протилежний.

Тепер поточний фронтенд передає **бажаний стан**:

| Запит | Значення |
| --- | --- |
| `PUT /api/posts/<id>/like` | Лайк цього автентифікованого користувача має існувати |
| `DELETE /api/posts/<id>/like` | Лайк цього користувача має бути відсутній |

Повторення PUT не створює другу пару; повторення DELETE не відновлює лайк. Така семантика відповідає ідемпотентним методам PUT/DELETE: [RFC 9110, idempotent methods](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2).

Ідемпотентність стосується потрібного ефекту, а не однакових байтів відповіді: кількість лайків інших користувачів між двома запитами може змінитися.

## Що змінилося у коді

| Файл | Роль |
| --- | --- |
| `post/repository/LikeWriteRepository*.java` | Атомарний upsert потрібної пари |
| `post/repository/LikeRepository.java` | Підключення фрагмента репозиторію |
| `post/service/LikeService.java` | Явне встановлення стану, перевірка допису, обробка конкурентного запису |
| `post/dto/response/LikeState.java` | Єдиний результат `likedByMe, likesCount` |
| `post/controller/PostController.java` | PUT/DELETE; ID користувача тільки з автентифікації |
| `frontend/src/api/postApi.js` | `setLike(postId, liked)` та перевірка JSON-відповіді |
| `frontend/src/pages/Feed/Feed.jsx` | Optimistic update, підтвердження сервером, rollback і видима помилка |

Префікс Java-шляхів — `backend/src/main/java/com/net/cardo/xcopybackend/`.

## 1. Як виконується PUT

1. Контролер визначає поточного користувача за перевіреною сесією. Клієнт не може передати ID іншого користувача в тілі й поставити лайк від його імені.
2. Сервіс перевіряє `existsActiveById`: допис має існувати й не бути позначеним для видалення.
3. Репозиторій виконує upsert за точною парою `postId, userId`.
4. `$setOnInsert` задає `postId`, `userId` та `createdAt` тільки при створенні. На повторенні існуючий документ, його ID і початкова дата не переписуються.
5. Наявний унікальний індекс із попереднього кроку захищає пару на рівні MongoDB, включно з паралельними процесами.
6. Якщо конкурентна вставка дала duplicate-key, сервіс перевіряє існування саме потрібної пари. Якщо вона є — бажаний ефект досягнутий. Якщо немає — помилку іншого обмеження не приховуємо.
7. Повторно перевіряється активність допису. Якщо він зник під час запису, щойно поставлений лайк прибирається, і повертається 404. Аварію до цієї перевірки додатково покриває фонове очищення сиріт.
8. Повертається підтверджений стан операції та актуальний `countByPostId`.

Приклад звичайної відповіді:

```json
{ "likedByMe": true, "likesCount": 1 }
```

При восьми одночасних PUT однієї пари фінально має бути **один документ**, що перевіряється реальною MongoDB у тесті.

## 2. Як виконується DELETE

Сервіс видаляє документи тільки власної пари `postId, userId`. Якщо запису вже немає, видаляти нічого — ефект однаковий. Чужі лайки не зачіпаються.

Для активного допису повертається `likedByMe=false` і поточна загальна кількість. Якщо допис уже видалений чи позначений для видалення, DELETE також успішний і повертає `false, 0`: користувацький лайк відсутній, ресурс більше не активний.

Це навмисно відрізняється від PUT: ставити новий лайк відсутньому допису не можна, тому PUT дає 404; прибрати свій старий лайк можна повторювано.

## 3. Що робить фронтенд

1. Кнопка визначає `nextLiked = !previousLiked` один раз для поточної дії.
2. Одразу показує цей стан і попередньо додає/віднімає одиницю — optimistic update.
3. Поки запит триває, кнопка вимкнена, щоб не запускати другу дію того самого компонента поверх першої.
4. `setLike()` надсилає PUT для `true`, DELETE для `false`. Автоматичного повторення запису в мережевому клієнті не додано.
5. Відповідь має містити саме boolean `likedByMe` і невід'ємний цілий `likesCount`. Відповідь з іншим ім'ям поля не вважається успіхом.
6. Успішний результат замінює попередні локальні значення серверними.
7. Помилка повертає попередній стан і кількість та показує повідомлення біля допису. Наступне натискання повторить бажану дію, а не залежатиме від невідомого стану серверного toggle.

Приклад втрати відповіді:

```text
UI: false → користувач натиснув → PUT → сервер зберіг true
Відповідь загубилася → UI відкотився до false і показав помилку
Користувач повторив → знову PUT → сервер залишив true, а не переключив у false
Підтвердження отримане → UI показує true та серверну кількість
```

Джерело істини — MongoDB і відповіді сервера. Читання/запис старого `x-copy-liked-post-ids` у `localStorage` прибрані. Старий ключ, якщо залишився в браузері від попереднього релізу, більше не впливає на інтерфейс. Після перезавантаження береться `likedByMe` з відповіді стрічки, а не стан іншої колишньої сесії браузера.

## 4. Кеш і кількість лайків

Готовий персональний DTO не кешується: сторінки містять спільні дописи, а лічильники й `likedByMe` підвантажуються свіжими пакетними запитами. Тому PUT/DELETE не очищають кеш усіх стрічок і не повинні змінювати застарілі числові поля всередині `Post`.

Локальне `+1` — тільки тимчасове відображення. Остаточний `likesCount` надходить із сервера й може врахувати інші одночасні дії.

Запис, перевірка активності та count — різні операції. Відповідь не є атомарним знімком усіх одночасних PUT/DELETE і видалення поста. Інша вкладка або користувач можуть змінити стан після виконання нашої операції. У наступній відповіді стрічки клієнт знову отримає актуальні дані.

## 5. Сумісність і обмеження

Старий POST-toggle залишений і позначений `@Deprecated` для попереднього фронтенду. Він **не став ідемпотентним**: старий клієнт не передає намір чи ключ конкретної операції, тож сервер не може відрізнити повтор від нового натискання. Поточний фронтенд його не викликає. Видалення legacy endpoint — окремий крок після переходу клієнтів.

При поетапному оновленні спочатку потрібен backend з новими PUT/DELETE, потім новий frontend. Перехід назад до POST при мережевій помилці не додається, бо він повернув би небезпечну семантику toggle.

Ідемпотентність не встановлює загальний порядок протилежних команд з різних вкладок. Запізнілий PUT після нового DELETE може знову встановити лайк; для суворого порядку намірів потрібні версії/умовні запити. Повторення однакової команди без протилежної проміжної зміни має однаковий потрібний ефект.

Для лайка природний ключ — пара «допис, користувач», тому окремий `Idempotency-Key` для PUT не потрібний. Для створення нового поста чи коментаря це інше завдання: автоматично повторювати їх без ключа операції все ще не слід.

## Перевірки

`ExplicitLikeTest` перевіряє повторні PUT/DELETE, відсутній пост, duplicate-key race, неприховану сторонню помилку та компенсацію лайка/коментаря при одночасному видаленні. Також перевіряються 404/403 для видалення коментарів замість загального 500.

`LikeIdempotencyIntegrationTests` використовує справжній Spring Data fragment і унікальний індекс: повторення зберігає один ID/початкову дату, вісім паралельних PUT створюють один запис, позначений допис відхиляє PUT і дозволяє повторний DELETE.

Frontend unit-тести перевіряють методи PUT/DELETE, cookie/CSRF-контракт, відмову від неоднозначного JSON і помилки мережевого запиту.

Браузерний сценарій виконує справжній PUT через backend, потім навмисно обриває тільки відповідь. Перевіряє, що сервер уже має один лайк, UI показав rollback, повторне натискання лишило один лайк, повторні DELETE не відновили його, а перезавантаження читає серверний стан. Це ін'єкція мережевого збою, а не підміна даних API вигаданим JSON.

## Як пояснити на співбесіді

«Toggle не містить наміру: однаковий запит може то додати, то забрати лайк. Я зробив ресурс лайка поточного користувача: PUT означає забезпечити його існування, DELETE — відсутність. Upsert із setOnInsert та унікальний індекс роблять повторення й паралельні вставки безпечними, а DELETE повторюється без відновлення стану. Фронтенд оптимістично оновлюється, але підтвердження й кількість бере із сервера, без localStorage як другого джерела. Я перевірив реальну втрату відповіді після запису і повторне натискання. Ідемпотентність вирішує повтор однакового наміру; порядок протилежних команд з різних вкладок потребує окремого механізму».
