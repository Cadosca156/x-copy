# Як працюють повідомлення про помилки

Сервіс визначає **причину** помилки конкретним класом винятку, а `GlobalExceptionHandler` визначає **HTTP-відповідь**. Для кожного бізнес-типу є окремий метод з `@ExceptionHandler`. Повідомлення повертаються в наявному форматі `{message, status, timestamp}`, який уже читає фронтенд. До відповідей додається `Cache-Control: no-store`.

Наприклад: коментар до відсутнього допису → `PostNotFoundException` → `handlePostNotFound()` → HTTP 404 з повідомленням «Допис не знайдено». Спроба видалити чужий коментар → `CommentAccessDeniedException` → окремий обробник → HTTP 403. Відсутній користувач поточної сесії → `AuthenticationRequiredException` → HTTP 401 з пропозицією увійти знову; раніше коментарі кидали загальний `RuntimeException`.

| Тип | Статус | Значення |
| --- | --- | --- |
| `InvalidPostException`, `InvalidCommentException` | 400 | Некоректний вміст |
| `InvalidPaginationException`, `InvalidCursorException`, `InvalidAuthorException` | 400 | Некоректні параметри читання |
| `PostNotFoundException`, `CommentNotFoundException` | 404 | Запис відсутній або вже видалений |
| `PostAccessDeniedException`, `CommentAccessDeniedException` | 403 | Дія заборонена поточному користувачу |
| `AuthenticationRequiredException` | 401 | Необхідний повторний вхід |
| `InvalidLoginRequestException`, `InvalidUsernameException`, `InvalidPasswordException` | 400 | Некоректні облікові дані або поля |
| `UsernameAlreadyExistsException` | 409 | Конфлікт зайнятого імені |
| `InvalidFollowRequestException` | 400 | Спроба підписатися на себе |
| `InvalidTwoFactorCodeException` | 400 | Неправильний код, виправлено колишній 502 |

Існуючі бізнес-типи для email та користувачів також мають окремі обробники. У нових винятках немає залежності від HTTP: класи успадковують `RuntimeException`, щоб не вимагати `throws` у кожному виклику, але код створює **конкретний тип**, а не `new RuntimeException(...)`.

Окремі обробники є й для некоректного JSON, типів/відсутніх параметрів, заголовків, завеликих завантажень, відсутніх ресурсів, непідтримуваних методів та форматів запиту. Зберігаються протокольні заголовки, наприклад `Allow` для 405. Тимчасова недоступність бази/черги/пошти повертає 503 з `Retry-After: 2`.

Невідомий виняток залишається 500: подробиці пишуться в серверний журнал, клієнт бачить загальне повідомлення без шляхів, SQL чи stack trace. Загальний `IllegalArgumentException` навмисно не перетворюється на 400: він може означати помилку програмування. Помилки конфігурації та компенсаційні `catch (RuntimeException)` у роботі зі сховищами не є користувацькими бізнес-помилками й зберігають свою поведінку.

Для існуючих сервісів авторизації та медіафайлів збережено сумісний обробник `ResponseStatusException`; ця зміна не переводить кожну їхню перевірку на новий клас. Помилки, які формуються security-фільтрами до MVC, продовжують оброблятися на рівні фільтрів.

Перевірки включають HTTP-мапінг кожного бізнес-типу, реальні виклики сервісу коментарів через контролер, заборону видалення чужого коментаря, відсутнього користувача сесії, неправильні параметри/JSON, захист внутрішніх повідомлень і перевірки username до запису в базу. Наявні тести часткових збоїв та повторних лайків тепер очікують конкретні бізнес-типи.
